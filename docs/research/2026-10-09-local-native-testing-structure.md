# Native test coverage migration design

Date: 2026-10-09. Baseline: `9a02def`. This is a design based on source inspection and an existing saved native test log. No simulator, build, or test was started. No application, test, workflow, or hook was changed.

## Decision

The repository already has the right lower-layer tools: real SQLite stores, real learning controllers and native media runtimes, SwiftUI views hosted in an actual `UIWindow`, pixel assertions, geometry measurements, and genuine UI automation. The opportunity is to redistribute assertions across those tools, rather than replace the application with a test representation.

The saved run makes UI automation the dominant cost. It does not establish that the expensive cases are redundant. Most player tests combine representation, touch interaction, committed persistence, and sometimes real media or process lifecycle in one method. Remove a method only after every unique assertion has a named replacement or retained UI assertion. Preserve all stage, media, text-size, failure, and durability distinctions that the original method actually tests. Do not impose a UI test quota.

For an immediate runtime experiment, prefer the coordinating review's condition-preserving UI existence prechecks with the same fallback wait and a separately measured two-worker pilot. Those mechanisms are distinct from coverage migration. For the first coverage migration intended to remove repeated launches, use the options row/order matrix below. The progress digit boundary is a useful disproof exercise, but keeping its full UI traversal would not establish worthwhile savings.

## Evidence boundaries

| Contract | Lowest suitable evidence | Evidence still needed from genuine UI automation |
| --- | --- | --- |
| Pure stage rules, XP, group accounting, numeric snapping | Domain/persistence/foundation package test, preferably through public command boundaries and real SQLite for durable behavior | Correct visible action calls the right command and displays its committed result |
| Actual SwiftUI pixels, relative frames, fixed bars, shared layout | App-hosted integration test rendering production views in a real `UIWindow` on iOS 27 | Real scrolling, taps, native presentation, or accessibility frames whenever those were original assertions |
| A rendered control's hit region | Native UIKit hit-testing can complement geometry and detect intercepted points | A successful real tap still needs XCUIAutomation for SwiftUI controls; `UIView.hitTest` alone does not prove the SwiftUI button action or system dispatch |
| Hidden text accessibility, selected traits, reading order | Production presentation values are useful supporting checks | Actual app accessibility snapshot/audit; a debug geometry preference is not accessibility evidence |
| Failed/pending save and committed editor values | Real `ProductModel`, `LearningController`, `SQLiteLearningStore`, and hosted editor composition | Retry and disabled-control wiring, focused text-field editing, keyboard Done/reset behavior |
| Reopening a store | Fresh SQLite connection and reconstructed controller/model | Process termination/relaunch when the original contract includes application bootstrap, launch arguments, scene ownership, or no autoplay |
| Audio/video/reveal completion | Existing real transport/lifecycle integration tests; no fabricated completion callback for transport acceptance | A rendered confirm action unlocks after native completion and awards only after the user's explicit action |
| Application backgrounding, foreground, sheets, edge-back, Apple dictionary, pasteboard | Native integration is valuable for ownership/state behavior | OS/user gesture and scene wiring remain genuine UI journeys |

An accessibility identifier does not prove that an element is visible, reachable, or eligible for VoiceOver. A successful direct controller call does not prove a button is wired. A component render cannot prove its placement inside the app navigation root. Keep these claims separate in the coverage ledger.

## Small disproof exercise: progress digit boundary

Scope: `PlayerUITests/testProgressTrackWidthSurvivesCounterDigitBoundary` and `PlayerLayoutRenderingTests/testProgressWidthSurvivesCounterDigitBoundary`. The current original case costs 27.042 seconds. Removing only two geometry assertions may save little because launch, traversal, and snapshots dominate. The entire 27.042 seconds is an upper bound on original work in scope, not a saving estimate.

1. Add a full-player native integration case using the bundled 12-source catalog, a disposable real SQLite store, `ProductWorkspace`, `ProductModel`, `LearningFlow`, and the actual `LearningPlayerView`. Existing `withPlayer` is a useful pattern, but its synthetic two-source catalog is insufficient for this contract.
2. Prepare the lesson with `startWhenPresented: true`, suspend before hosting, and ensure the view's presentation task cannot start practice unexpectedly. Drive selection through `runtime.coordinator.editWhilePaused(.selectSource(8))` and then source 9. Do not assign a fabricated counter. Wait for settled measured production geometry after each committed transition.
3. Require the committed session to identify source 8 then 9, unit count 12, paused status, zero XP, and zero completed runs. Check the actual counter representation and progress frame, using the original 0.5-point tolerance for width and `minX`. Reopen the store through a new connection to check the saved cursor/paused checkpoint, while documenting that this does not replace process relaunch coverage.
4. Preserve the genuine UI traversal: bundled book selection, stage opening, all-sentences navigation, real source-8 and source-9 taps, visible `9/12` and `10/12`, sheet dismissal, and `학습 이어하기`. Preserve the existence of a real visible progress element. Existing `testAllSentencesSelectsPausedWithoutCredit` uses a two-source fixture and cannot silently replace the bundled 12-source traversal or its scroll reachability.
5. Once the native case and its disproof checks pass, move only the width and `minX` comparison to native integration. Keep the UI method as the binding/gesture assertion owner. Any later removal or merging of that UI method must preserve its exact bundled fixture, two source selections, and visible results in a retained genuine UI journey.

Disproof checks for an implementation branch must include temporarily removing the hidden maximum-width counter reservation in `PlayerTitleView`, rendering an incorrect counter after a correct committed selection, routing a source row to the wrong index, leaving playback resumed after selection, and introducing a transparent touch interceptor over the source row. The native geometry case must catch the reservation regression; native/controller checks must catch state regressions; genuine UI checks must catch wrong visible binding and interception. Do not commit these mutations. If either test remains green under the fault it is intended to detect, the proposed replacement is insufficient.

This slice needs no new package or third-party snapshot library. Reuse the existing production geometry seam and native rendering helpers. Helpers must reject missing/zero frames, wait for actual settlement, report failed settlement, close runtimes, deactivate models, release hosting controllers/windows, and remove only their disposable roots. Do not add production launch flags that bypass the normal player composition.

## First migration that can remove repeated UI work: options rows

Target `testPlayerOptionsMatchSettingsOrderForAudioAndSilentStages`, whose two launches cost 65.030 seconds in the saved run. This method's unique obligations are the six row positions at stages 1 and 11, the audio versus silent speed title and destination, real close/exit, and zero XP. Existing UI cases cover much of close/exit and zero XP but do not automatically prove the menu-to-speed route for both stages.

The proposed replacement has three concrete owners:

1. A new native integration case hosts the actual `LearningOptionsView` inside its production navigation/sheet composition, with a real stage-1 flow and then a real stage-11 flow. It measures all six actual row bounds in the original order, renders the stage-specific speed label, and uses real saved state to prove options entry/exit earns no credit. Do not assert only the `LearningOptionRoute.preferences` constant. Add narrowly scoped production frame diagnostics only if the existing geometry mechanism cannot observe these rows; a diagnostic frame must describe the actual row, not a reconstructed array.
2. Retain the stage-1 genuine menu-to-rate transition in an already-required stage-1 audio journey, preferably `testRealAudioConfirmationAndPausedMenu`. On its existing options opening, require the actual audio speed row, tap it, require navigation title `배속`, then close the sheet and retain its paused/credit checks. This adds navigation work but no new launch or separate lesson entry.
3. Change the already-required stage-11 completion/relaunch journey `testBriefRewardsPreserveCompletionWithoutReplayOnRelaunch` to open options and the silent speed row before completion, require title `단어 공개 속도`, then close and resume explicitly as needed. Its stage-11 fixture and completion/relaunch contracts remain unchanged. Stage-15 silent-speed coverage alone is not an exact replacement for the original stage-11 condition.

Keep actual accessibility row exposure/title evidence for both stage variants in these retained journeys. Retain the same six original AX frame-order assertions while the already-open menu is visible. That preserves the original frame source and tolerances while still allowing removal of the two standalone launches and duplicate book/stage traversal. The native matrix then protects representation independently; it is supporting evidence, not claimed AX parity.

After overlap verification and the negative controls below pass, remove the standalone row/order UI method. Its 65.030 seconds is the maximum original case work available. The actual saving is `65.030 s - added native cases - added retained UI work`, plus any changed runner overhead. This could be worthwhile because it removes two full launches and repeated setup; it is not a 65-second promise. If the retained journeys cannot own all six rows and stage-specific menu routes without hiding failures, keep the original method and record that migration as blocked by equivalence, not complete.

Disproof controls: reorder only the rendered option rows while preserving the route constant; substitute `배속` at stage 11; wire the silent menu speed row to the audio editor while preserving its label; detach the tap action; make the close action resume playback; and award XP on options exit. Render/order faults must fail the native render or retained exact AX order checks. Route and tap faults must fail genuine UI. Pause/credit faults must fail real-store/controller and genuine UI assertions. The stage-11 journey must still pass real completion and relaunch after the new navigation sequence; never bypass reveal completion to save time.

The same mechanism can later replace duplicated summary/preview traversals: prepare all representation combinations through real model/controller state, keep each distinct control/navigation boundary in an existing relevant journey, and delete an old method only once its complete obligations have named owners. Add assertions to a screen already visited when that preserves the original environment; do not retain an entire old traversal merely to claim that its assertions moved.

## Architecture for larger savings

Use a reusable app-hosted fixture, rather than a second product implementation. It should own a disposable SQLite root, actual catalog, actual `ProductModel`, actual `LearningFlow`/runtime, real `UIWindow`, and actual production root view. A fixture can expose deterministic committed-state preparation through public model/coordinator commands; it must not mutate private SwiftUI state, fabricate saved snapshots, or simulate native media completion for tests claiming media acceptance.

Separate representation from operating-system workflows in the assertion ledger. A representation case can prepare a paused or completed state through domain/controller commands when native playback is explicitly outside that case's scope. Pair it with retained real-transport and genuine UI tests for native completion and explicit confirm. This avoids replaying native audio merely to inspect every style/text-size combination while preserving proof that actual playback completion reaches the real controls.

Use current seams before changing production interfaces. `PlayerLayoutMeasurements` already observes production frames. `ProductTabsView`, `LearningPlayerView`, `LearningContentView`, `TypographyPreview`, and `PreferenceEditorView` already accept model/value dependencies. The private `PlayerHeaderView`, `StudyStatusView`, `RevealPresetRow`, and editor-local `@State` mean some behavior is only reachable through actual composition. Do not expose a test-only shadow view or extract a state machine just to make a green test. Any later production extraction must preserve the actual control's binding and normal lifecycle.

Create focused native integration suites for full-player composition, option/editor committed behavior, shared text layout, and real browsing toolbar/resource rendering. Reuse immutable fixture bytes where safe, but keep mutable database/profile/window/runtime ownership per test. Serialize UIKit/AVAudioSession/MPNowPlayingInfoCenter-dependent work at the necessary scope. The existing mixture of XCTest and Swift Testing means a `.serialized` suite is not a process-wide lock.

Preserve OS journeys with specific assertion owners: app entry, true audio/video completion plus explicit confirm, failed-save retry plus relaunch, Home/activate, native sheets and edge-back, dictionary/pasteboard, largest-text scroll/touch, and VoiceOver audit/snapshot environments. They can share setup or collect multiple related assertions in one coherent journey, but that changes isolation and failure diagnosis. Do not consolidate unrelated flows until deterministic setup and attribution are demonstrated. If two old methods are merged, list every original assertion, environment, state transition, and failure mode in the migration ledger.

Negative controls for later slices should include leaking hidden full text only into accessibility, preserving good model values while showing stale editor state, displaying optimistic preset values before save, resetting global presets into an active run, reusing old grouping after a committed retry, placing reward in normal layout so it moves lesson text, accidentally applying video list override to saved global defaults, intercepting a touch target without changing its frame, attaching video to silent stages, double-awarding a lost-reply retry, and resuming on foreground. Each fault needs a declared detector in its correct layer. Lower-level green plus UI red can be the expected evidence boundary, not a reason to weaken UI.

## Acceptance and timing rules

For each implementation slice, run the added native tests and the affected genuine UI tests against the same iOS 27 application products, then the unchanged complete gate. Compare the original and replacement obligation inventories. During overlap, all original UI tests continue to execute. Removal requires passed replacement evidence and disproof checks for the intended failure classes, followed by a complete fresh run. No skips, ignored failures, weaker tolerances, shorter condition limits, fabricated playback-ended buttons, stale-commit PASS reuse, or changed required remote checks count as completion.

Record original case duration, new native duration, retained/merged UI duration, launch/tap counts, runner/build/result overhead, and total full-run wall time. A case's duration is the maximal original work attributable to that case. A removed method's unique UI obligations still need explicit owners; their retained or merged execution cost must be included. Net saving is measured after adding replacement/retained work; it is not the sum of candidate original case times.
