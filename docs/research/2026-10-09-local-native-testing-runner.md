# Local native runner, cache, and isolation audit

Date: 2026-10-09. Source baseline: `9a02defbef3737b30a3794315507570f8e1c3985`.

The strongest runner-only candidate is two explicitly partitioned UI executions on two isolated iOS 27 simulators. It requires a measured experiment before adoption. Across all audits, first trial the smaller immediate-existence check with its unchanged conditional-wait fallback, then this concurrency pilot, before broader assertion-preserving renderer migration. Build caching is a small secondary opportunity: compilation accounts for approximately 82 seconds of the recorded 47-minute run. Reusing a prior PASS for a different commit would violate the current local gate, including when only documentation changes.

This note is research and design only. No simulator was created, booted, installed, erased, or deleted. No native test, hook regression, or full runner was executed. Application source, tests, hooks, CI, required checks, and release approval remain unchanged. Existing result JSON, source files, and the installed `xcodebuild -help` were read. The coordinating investigation supplied the local hardware inventory: 10 physical/logical cores and 16 GiB RAM. Resource capacity under two simultaneous simulator workloads has not been measured.

## Evidence and priorities

The [timing audit](2026-10-09-local-native-testing-timing.md) reconstructs 2,832.519 seconds of full-runner time. UI methods consume 2,669.439 seconds, or 94.243%. The 105 integration declarations consume 45.917 seconds of test-body time. Debug, Release, and fictional downloader compilation total 81.672 seconds. The native suite has 183 compiled identifiers: 78 UI methods and 105 integration declarations. Parameter-expanded executions are a different counting boundary; the recorded per-device count is 235. The six host package suites are a separate gate and are excluded from these timings.

| Rank | Candidate | Expected scale from current evidence | Decision |
| --- | --- | --- | --- |
| 1 | Two isolated UI selections, internally serial | Can substantially shorten the UI critical path if local contention is low | Design a controlled pilot; no speedup is verified |
| 2 | Reduce expensive UI setup/synchronization while preserving public assertions | Potentially substantial, but requires individual test evidence | Follow the assertion and timing audits; outside this runner-only proposal |
| 3 | Reuse validated compilation or overlap independent builds | Approximately 82 seconds is the measured ceiling for eliminating all compilation | Secondary; retain every build/product guard |
| 4 | Warm simulator, faster result export, fewer console lines | Readiness was 0.153 seconds and result export approximately 1.431 seconds | Marginal in this successful local run |
| Excluded | Cross-commit PASS reuse, omitted tests, shorter blanket timeouts, retries that hide failures | Apparent reductions would alter evidence or policy | Do not adopt |

The [Apple research](2026-10-09-local-native-testing-apple.md) and [open-source research](2026-10-09-local-native-testing-oss.md) support partitioned execution and one build reused by consumers. They provide no evidence that a particular number of simulators will be efficient on this Mac. Apple's distributed XCTest description allocates classes nondeterministically and recommends identical destination hardware and OS versions. Explicit selectors provide a more inspectable local partition. Merely adding two destinations can instead execute the entire suite twice under destination testing. [Apple: Get your test results faster](https://developer.apple.com/videos/play/wwdc2020/10221/).

## What the current gate already guarantees

The [.githooks/pre-push](../../.githooks/pre-push) entry invokes [native-pre-push.rb](../../native-ios/scripts/native-pre-push.rb). The hook parses all pushed nondeletion OIDs, resolves each as a commit, and disables Git replacement objects. It checks the committed full-runner marker against contract version 4 before consulting the PASS cache. It rejects committed private `Local.xcconfig` and archives exactly the pushed commit's `native-ios` and `assets` paths. It does not test dirty working files. The archive is extracted into a private system temporary directory outside the original Git repository, with a private snapshot-local `TMPDIR` and stripped Git environment.

The [full runner](../../native-ios/scripts/test-native-full.sh) refuses a checkout with `.git`, private configuration, missing tools, a non-Xcode-27 toolchain, or an unresolved simulator. It requires an explicit available simulator from `com.apple.CoreSimulator.SimRuntime.iOS-27-0`, named with the `MetaShadowing Native Pre-push` prefix. It does not accept the W2 preview simulator or a physical device. It clears inherited private-video, SDK, toolchain, xcconfig, and Git context overrides while retaining the selected Xcode.

The runner already generates the fictional CI project once, builds an arm64 Debug `.xctestproducts` package once, inspects Debug, builds and inspects Release, builds the fictional downloader, and executes the runtime inspection regression. It waits for the dedicated simulator, enumerates the full compiled inventory, and runs `test-without-building -testProductsPath` with `-parallel-testing-enabled NO` and `-collect-test-diagnostics never`. Debug tests use ad-hoc simulator signing; Release remains unsigned. Recommending build-for-testing/test-without-building as a new optimization would duplicate existing behavior.

The [result validator](../../native-ios/scripts/validate-native-test-results.rb) rejects invalid/disabled/empty inventory, invalid selectors, selectors matching no compiled method, empty selections, failed/skipped summaries, incomplete counts, nonpassed nodes, duplicate argument runs, and a mismatch between selected compiled identifiers and finalized executed identifiers. It validates identities, not merely the headline count. Private logs/results are retained under the Git common directory; the hook publishes only approved progress/PASS lines. A PASS cache record is atomically published only after the complete runner succeeds.

The current cache identity includes contract version, exact pushed commit, `xcodebuild -version`, XcodeGen version, configured simulator ID, and runtime identifier. It therefore avoids an unchanged-commit push retry, but every new commit requires full testing. This is explicit in the [native README](../../native-ios/README.md), and [hook regression coverage](../../native-ios/scripts/test-native-pre-push.rb) checks exact-commit/toolchain reuse, failed validation, isolation, stale contracts, and cancellation. The cache is not a build cache.

## Offline scheduling estimate

The following calculation reads the existing case durations and assigns entire UI classes, largest first, to the least-loaded worker. It assumes durations do not increase, ignores runner duplication and contention, and performs no tests. It is a workload estimate, not a benchmark, target, guarantee, or proof that Xcode's nondeterministic scheduler would choose this allocation.

| UI workers | Largest predicted class bin | Meaning |
| --- | ---: | --- |
| 1 | 2,669.439 seconds | Observed accumulated UI method duration |
| 2 | 1,340.506 seconds | Greedy class partition, approximately 22m21s of UI work |
| 3 | 1,108.369 seconds | `PlayerUITests` class floor |
| 4 | 1,108.369 seconds | Same class floor; no further ideal gain |

`PlayerUITests` alone is 1,108.369140 seconds for 27 methods. Four workers cannot divide that class in Apple's described class allocation. Explicit method selectors can divide it, as the existing manual CI `player-options` selection does, but that is a different allocation with different overhead and isolation questions.

A concrete two-bin class partition is:

| Worker | UI classes | Methods | Sum of observed method durations |
| --- | --- | ---: | ---: |
| A | `PlayerUITests`, `NativeFoundationUITests`, `DownloadLabUITests`, `BookshelfUITests` | 38 | 1,328.933 seconds |
| B | `AppleServicesUITests`, `ProductUITests`, `ReferenceToolsUITests`, `VoiceOverSemanticsUITests`, `OfflineAcceptanceUITests`, `NativeMediaUITests`, `ProductAccessibilityUITests` | 40 | 1,340.506 seconds |

These bins are suitable for an initial bounded experiment, not a hardcoded permanent inventory. Future classes need an explicit owner or a fail-closed partition generator. Completeness must come from the current compiled inventory. Do not accept 183 as a permanent magic number.

Under this idealized calculation, UI parallelism saves approximately 1,328.933 seconds. Adding back the serial non-UI work gives roughly 25 minutes rather than 47 minutes before new overhead. That is an optimistic planning comparison, not an expected measured duration. A serial integration phase also adds its own runner/install/finalization overhead. Three or four simultaneous UI workers promise much less additional ideal benefit and consume more memory; they should not be the first local experiment.

## Isolation audit

The source supports filesystem isolation, but does not prove complete simulator/host resource independence.

- **Durable profiles and fixtures:** UI helpers pass UUID probe identifiers. [MetaShadowingApp.swift](../../native-ios/App/MetaShadowingApp.swift) selects `ProductTestProfiles/<UUID>`, `ProbeProfiles/<UUID>`, or `NativeDiagnostics/<UUID>` in the app container. Integration fixtures commonly use UUID temporary roots and remove only their own roots. Keep each journey's same UUID across its intentional relaunch; sharing profiles between workers or generating a new profile during a persistence check would invalidate the assertion.
- **Audio and remote ownership:** [NativeLifecycleTests](../../native-ios/Tests/MediaIntegrationTests/NativeLifecycleTests.swift) changes `AVAudioSession.sharedInstance()` category/activation and checks real now-playing state. [RuntimeObservationTests](../../native-ios/Tests/MediaIntegrationTests/RuntimeObservationTests.swift) saves, replaces, and restores `MPNowPlayingInfoCenter.default()` metadata. [LessonRemoteControl](../../native-ios/Packages/LearningMedia/Sources/LearningMedia/LessonRemoteControl.swift) installs shared remote-command targets and changes enabled state. Several suites use `.serialized`, but Swift Testing's serialization applies within a suite, not against unrelated suites. `-parallel-testing-enabled NO` is not a process-wide Swift Testing lock. Preserve existing framework scheduling; do not increase integration concurrency. [Apple: Running tests serially or in parallel](https://developer.apple.com/documentation/testing/parallelization).
- **Native media is still real:** [NativeMediaUITests](../../native-ios/Tests/AppUITests/NativeMediaUITests.swift) waits for native playback completion, checks no credit at media end, confirms explicitly, and relaunches durable state. Other UI tests run native audio/video. Separate simulator processes and app containers reduce collisions, but shared host audio hardware, media services, CPU, memory, WindowServer, and simulator services can still contend. No cross-simulator interference was reproduced by this audit. Do not mute, fast-forward, synthesize completion, or replace the native transport to make a parallel run pass.
- **Microphone evidence boundary:** [VoiceMonitorGainTests](../../native-ios/Tests/MediaIntegrationTests/VoiceMonitorGainTests.swift) renders generated signals through an offline `AVAudioEngine` graph. It does not capture a microphone. Retain those assertions; passing them does not establish live microphone or physical-device acceptance.
- **Device state:** UI tests press Home, activate their app, change appearance, run accessibility audits, and observe foreground behavior. [VoiceOver tests](../../native-ios/Tests/AppUITests/VoiceOverSemanticsUITests.swift) and [service appearance tests](../../native-ios/Tests/AppUITests/AppleServicesUITests.swift) change simulator appearance. [ReferenceToolsUITests](../../native-ios/Tests/AppUITests/ReferenceToolsUITests.swift) exercises copy behavior backed by `UIPasteboard.general`. UUID SQLite profiles do not isolate device appearance, SpringBoard, pasteboard, permissions, or foreground state. Each worker needs a different simulator; never run two selections on one device.
- **Rendering state:** Integration tests create windows in `UIApplication.shared.connectedScenes`. Their main-actor and suite annotations do not establish permission to run several independent rendering owners concurrently in one app process. The short integration phase offers little benefit from further splitting.

The initial experiment should run the complete integration target first, as one unchanged execution on simulator A, then run two UI selections concurrently on A and B. This avoids overlapping integration audio-session/global-state tests with a UI workload. It leaves real UI media overlap as a falsifiable risk. If UI media interference appears, reject unrestricted parallelism and evaluate resource-specific scheduling separately; do not hide it by relaxing assertions or timeouts.

## Proposed two-worker pilot contract

1. **Freeze inputs.** Use one committed source archive and the fictional CI configuration. Build and inspect Debug, Release, downloader, and runtime guards exactly as the current full gate does. Enumerate the complete compiled inventory once. Save private monotonic phase timing and artifact checksums. Do not operate on a dirty checkout or private identity.
2. **Provision separately.** A later implementation experiment needs two explicitly recorded dedicated pre-push test simulators of the same iPhone type and iOS 27 runtime. Reuse of W2, reference, or physical devices remains prohibited. Keep IDs local. Simulator creation/install/testing is outside this research scope and was not performed.
3. **Partition before executing.** Partition the full inventory into integration, UI A, and UI B. Require nonempty selections, pairwise disjointness, and union equality against the unfiltered compiled inventory. Reject unknown targets/classes until they have an owner. Selectors must come from those inventory identities, not unreviewed hand-written class assumptions.
4. **Stage immutable products.** Build once. Stage checksum-identical `.xctestproducts` into separate private worker directories if Xcode writes beside the package; give every execution its own result/log/output paths. Keep separate destinations and `-parallel-testing-enabled NO`. The installed Xcode help confirms `-testProductsPath`, `-resultBundlePath`, and worker flags, but confirms no speed or isolation guarantee. A full-suite duplicate run on both destinations is not partitioned execution.
5. **Preserve execution and results.** Run integration once, then the two UI selections. Retain existing diagnostic settings and ad-hoc simulator signing. Each execution must finalize a result bundle and pass the existing selected-inventory validator. Aggregate all executed identities and require exact union equality with no duplicates, failures, skips, expected failures, cancellation, empty shard, or missing result. Keep parameter-run validation and original failures. All 183 current declarations must be represented; the count may grow with future source changes.
6. **Drain before releasing ownership.** The current hook places its heavy runner in an owned process group and retains the repository lock if cancellation cannot drain it. A fan-out coordinator must track every child and process group, stop and reap both workers on interruption/failure, and avoid orphaning the sibling. Host process-group drainage alone does not prove simulator guest apps stopped. Verify guest test/application activity has settled on the exact owned simulators before reuse. Cleanup must target only experiment-owned processes/devices; never `killall`, shut down all simulators, erase reference devices, or delete unrelated data. If drainage cannot be established, retain ownership locks and publish no PASS.
7. **Lock all destinations.** The existing Git-common lock prevents concurrent hooks within one repository and its worktrees; it does not protect the same simulator from another clone or manual runner. A future coordinator needs per-simulator locks shared across local consumers, in addition to the repository lock. Acquire multiple simulator locks in deterministic order, record private owner PIDs/run IDs, and release only owned locks after drainage. Do not automatically delete a stale-looking lock while its owners or guest activity are unresolved.
8. **Measure the whole run.** Compare serial and parallel executions of the same revision, compiled inventory, fixture bytes, device type, runtime, Xcode, signing, and assertions. Record end-to-end time, phase/shard time, CPU load, memory pressure, swap growth, and all original failures. Use lightweight bounded sampling. The saved serial run is useful baseline evidence but cannot isolate cold-device/order effects by itself. A second clean controlled pair is appropriate only if an initial success or unresolved variance warrants it. Do not add automatic retries to the gate.
9. **Adopt only measured success.** Require complete unchanged coverage, stable real media/lifecycle behavior, clean cancellation, and lower full wall time. Keep a serial diagnostic path. A failed parallel experiment remains a failure even if a later serial run passes; the later result diagnoses scheduling risk. Changing the real hook would require consistent contract-version updates, expanded isolation/partition/cancellation regressions, and fresh full verification. This note makes none of those changes.

## Compilation cache design and policy boundary

The current fresh archive and fresh DerivedData avoid accidental authority from old products. Incremental compilation can be treated as a hint only when Xcode still evaluates the current archived inputs and every product/result guard remains authoritative. It cannot authorize a PASS before current-commit native execution completes.

For a future immutable artifact cache, keep separate keys for test products, Release, and downloader configuration. Bind reusable products to normalized archived inputs, file types/modes and bytes, `native-ios` and public `assets`, all scripts/project/configuration/package inputs, dependency resolutions if introduced, Xcode build version, Swift compiler, XcodeGen, simulator SDK build, arm64 architecture, destination platform, signing/build settings, permitted environment inputs, and runner contract. Include digest of the actual produced package and validate metadata before execution. Canonicalized paths and machine details remain private. Git archive attributes/export substitutions can affect materialization; native/assets tree hashes alone are insufficient if archive behavior or relevant attributes change. Generate/hash the actual normalized archive input manifest.

The existing [CI product transport](../../native-ios/scripts/ci-test-products.sh) validates revision, toolchain, and checksum and explicitly describes itself as a run-scoped transport, not a cross-commit build cache. Reuse its validation principles; do not relabel an old revision to satisfy it. `.xctestproducts` portability also does not make arbitrary DerivedData path-sensitive state reusable. Reject corrupt/incomplete metadata and use a fresh build for an ordinary cache miss; never silently substitute a stale artifact. Cache publication requires completed builds, checksum validation, private permissions, and atomic ownership. No cache policy or artifact is changed here.

When a documentation-only commit produces exactly identical normalized build inputs, compilation reuse could save some of the measured 81.672 seconds. Debug/Release product inspections, downloader guard semantics, runtime regression, enumeration, and all current-commit executions still run. Exact-input reuse must not copy a prior PASS to the new commit. The current owner policy explicitly requires new commits to undergo full testing; an input-equivalence exception for PASS reuse would be a separately approved policy change and is outside this proposal.

Artifact reuse across failed pushes of the same commit has a narrower identity risk, but the successful exact-commit PASS cache already removes all work after a completed success. Persistent build caching primarily helps failed-run repetition or identical-input new commits. Its engineering and invalidation cost should be justified by measured savings. It cannot turn a 47-minute UI-heavy run into a short verification cycle.

## Recommendation

Prepare one two-worker UI pilot with all integration tests in a preceding unchanged serial phase, exact inventory aggregation, two destination locks, and complete cancellation handling. Measure it before changing the pre-push gate. Continue assertion-preserving UI cost reduction as the separate larger opportunity identified by the other audits. Defer persistent compilation caching until those experiments expose a meaningful remaining build cost. Preserve full local pre-push acceptance, required remote checks, human release approval, iOS 26.0 deployment minimum, iOS 27 verification, real media completion, explicit credit, durable relaunch, and all existing assertions.
